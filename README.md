# floodsense-sql

A read-only SQL endpoint that speaks the Zetaris REST call the FloodSense
agents make, over a Postgres holding the four contract views.

**This is not Zetaris.** Zetaris is a licensed engine each person runs on
their own machine, and the monorepo is explicit that nothing in it may start
one (`compose.yaml`, `zetaris/README.md`). This service exists so the agents
can run against a real database now, and be pointed at the real engine later
by changing one environment variable.

It says so on every answer: `X-Engine: floodsense-sql` and `engine` in the
body. The agents record that and report it, so a run shows which engine
answered instead of claiming it reached Zetaris.

## The views

Ported from the monorepo, not invented here:

| view | rows | from |
|---|---|---|
| `floodsense_seed.hazard_timeline` | 576 | `zetaris/migrations/013` |
| `floodsense_seed.discharge_daily` | 136 | `zetaris/migrations/012` |
| `floodsense_seed.exposure_join` | 359 | `zetaris/migrations/016` over `ingestion/prep` |
| `floodsense_seed.provenance` | 8 | `zetaris/migrations/017` over `ingestion/prep` |

Row counts match the `min_rows` each migration declares. `app/seed/seed.sql`
is generated by `tools/build_seed_sql.py` against a monorepo checkout; it is
committed so the service needs nothing at run time. Regenerate it when those
migrations change — do not edit it by hand.

The Lightning SQL in those migrations does not run on Postgres, so the
translation is: `FROM VALUES (...)` becomes a table, `1.0D` becomes `1.0`,
`SCHEMASTORE VIEW ... WITH CONTAINER x` becomes a view in schema `x`. The
`SELECT` bodies are unchanged.

## The call

```
POST /api/v1.0/sql-editor/sqls/run
Authorization: Bearer $SQL_API_KEY
X-Org-ID: 1
X-Request-ID: <uuid>

{"queryId": "...", "sql": "SELECT ...", "limit": 20, "source": "SqlEditor"}
```

Answers `{"engine", "queryId", "headers": [{"name"}], "data": [[...]]}`.
`GET /api/v1.0/auth/login` returns the same key as `idToken`, for callers
configured with a user and password instead of a key.

Reads only, two doors: the statement must be a single `SELECT`/`WITH` with no
write keyword, and the connection is `READ ONLY` with a statement timeout.

## Running it

| variable | |
|---|---|
| `DATABASE_URL` | provisioned by the platform (`database: true`) |
| `SQL_API_KEY` | the bearer token callers present (required) |
| `SQL_SCHEMA` | default `floodsense_seed` |
| `SQL_ROW_CAP` | default 5000 |
| `SQL_STATEMENT_TIMEOUT_MS` | default 20000 |

```bash
docker run -d --name fs-pg -e POSTGRES_PASSWORD=test -e POSTGRES_DB=floodsense \
  -p 55432:5432 postgres:16-alpine
DATABASE_URL=postgresql://postgres:test@127.0.0.1:55432/floodsense \
  SQL_API_KEY=local-dev-key PORT=8101 python -m app
```

Then point the agents at it:

```bash
ZETARIS_REST_URL=http://127.0.0.1:8101/api/v1.0 ZETARIS_API_KEY=local-dev-key \
  ZETARIS_ORG_ID=1 python -m floodsense_agents
```

`GET /ready` reports the row count of each of the four views, and returns 503
if any is empty.

## Switching to the real Zetaris

Point `ZETARIS_REST_URL` at the Zetaris REST base (`…:8888/api/v1.0`) and set
`ZETARIS_API_KEY` from your own Zetaris UI. Nothing else changes: the agents
send the same SQL, and the audit panel will say the queries reached Zetaris
rather than naming this service.

## Reaching the real Zetaris from anywhere

Zetaris runs on `servingz`, which has no public IP, and its REST port is
bound to a tailnet. Anyone not on that tailnet cannot reach it. This service
can, because it runs on a node that is both public and on the tailnet, so it
forwards the one call the agents make:

```
POST https://floodsense-sql.zaindroid.me/zetaris/api/v1.0/sql-editor/sqls/run
GET  https://floodsense-sql.zaindroid.me/zetaris/ready
Authorization: Bearer $SQL_API_KEY
```

Point the agents at it by changing one variable, and nothing else:

```bash
ZETARIS_REST_URL=https://floodsense-sql.zaindroid.me/zetaris/api/v1.0
ZETARIS_ORG_ID=1
ZETARIS_API_KEY=<the same key as SQL_API_KEY>
```

Two things it adds over reaching the engine directly:

* **one shared key instead of the engine's admin password.** The password
  stays on `servingz`; a caller never holds it and it can be rotated without
  telling anyone.
* **the same read-only guard** this service applies to its own queries, so a
  leaked key cannot write through this door even though the engine itself
  accepts DDL.

It does not pretend to be the engine. Replies pass through untouched, so they
carry no `engine` field and no `X-Engine`, and an agent reading one reports
`zetaris` -- true, because the statement ran on Lightning. The hop is in
`X-Via`.

`/zetaris/*` is the real engine. `/api/v1.0/*` is this service's own Postgres
and still answers `X-Engine: floodsense-sql`. Same four views either way.
